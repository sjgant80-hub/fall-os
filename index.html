fall-os

One shared core, one conductor, composable organs.

fall-os is a deterministic runtime for orchestrating decisions and builds. Every tool becomes an organ that routes through a single shared core and a single control loop — so improving the core improves every organ at once. Mutation-tested, zero-dependency, and offline-capable.

What it is

An operating system for decisions, not a bag of tools

A conventional toolkit is a pile: each tool has its own logic for generating options, scoring them, committing to one, and caching the result — so every improvement has to be made in every tool. fall-os factors that shared machinery into one place. The result is a single system with one bloodstream and one control loop, into which any number of tools plug as organs.

Core

One shared engine

A single routine every organ calls: expand candidates, score them against a fixed threshold, commit deliberately, cache by content. Improve it once, everywhere improves.

Conductor

One control loop

A single loop — explore, resolve, verify, build, remember — that invokes organs in order. Organs are called by the loop; they never run standalone.

Organs

Composable capabilities

Forward search, reinterpretation, synthesis, memory, and a not-taken index all register against the same core. Adding one is registration, not integration.

How it works

Architecture

A conductor runs one control loop; every phase of that loop calls the shared core; organs register against phases. Because all expansion, scoring, commitment, and caching live in the core, a change there propagates to every organ.

The control loop

01ExploreExpand candidate branches with a golden-angle offset for near-uniform, low-overlap coverage.
02ResolveScore each candidate; a candidate holds at or above the threshold κ = 1/φ, otherwise it clashes.
03VerifyAn author (an automated check or a person) commits one candidate. Nothing is selected implicitly.
04BuildThe committed candidate is produced and cached by content, so identical inputs build once.
05RememberThe selection is recorded; every not-taken branch is written to the index for later retrieval.

        Engineering

        Correctness is enforced, not asserted

        Every module is checked by a mutation-testing gate on each push: the gate systematically alters one operator at a time and requires the test suite to catch it. A passing assertion suite is necessary but not sufficient — the gate proves the tests actually constrain behaviour. Surviving mutants are either killed by a new test or recorded as reviewed equivalents with a written rationale.

        Determinism

        Reproducible by construction

        No wall-clock, no randomness in the kernels. Identical inputs yield byte-identical results; content-addressed caching makes repeated work free.

        Zero dependencies

        Auditable surface

        Pure ES modules, no build step, no runtime packages. The browser demo imports the same source the tests and CI verify.

        Continuous verification

        Green on every push

        Assertion suites plus the mutation gate run in CI for all five modules. The published page and the gated logic are the same code.

        Grounded commitment

        Nothing selected implicitly

        The conductor only builds a candidate an author commits, and only one at or above the threshold. Below threshold, the field stays open.

        Total recall of alternatives

        The road not taken is kept

        Discarded candidates are content-addressed and indexed. A branch reconsidered across separate decisions accrues a recurrence count you can query.

        FAQ

        Frequently asked questions

        What problem does fall-os solve?

        Tools that generate options, score them, commit to one, and cache the result each reimplement that machinery. Improvements then have to be repeated per tool, and behaviour drifts between them. fall-os centralises the machinery in one core and one control loop, so a single improvement applies everywhere and behaviour is consistent by construction.

        What is the “core,” and why does everything route through it?

        The core is one routine: expand candidates with a golden-angle offset, score them against the fixed threshold κ = 1/φ, commit one deliberately, and cache by content. Every organ and every phase of the control loop calls it. Centralising expansion, scoring, commitment, and caching is what makes an OS out of a toolkit — improve the core, and every organ improves at once.

        Why κ = 1/φ, and what does “holds vs. clashes” mean?

        Scores are normalised to [0, 1]. A candidate holds when its score is at least κ ≈ 0.618 and clashes otherwise. κ = 1/φ (the reciprocal of the golden ratio) is used as a single, consistent acceptance threshold across the system; the value is a project convention, and the mechanism — one shared threshold — is what matters.

        What is the golden-angle offset for?

        Candidate branches are generated at successive multiples of the golden angle (≈ 137.5°). This produces near-uniform, low-overlap coverage of the option space — successive candidates spread out rather than clustering near the obvious first choice, which matters when you want genuinely divergent alternatives.

        What is the “not-taken index”?

        Every candidate that is generated but not committed is content-addressed and stored. Because it is content-addressed, the same branch reconsidered across different decisions deduplicates and accrues a recurrence count. You can query what you nearly built, retrieve the alternatives of a given decision, or rank by recurrence to surface a direction you keep revisiting but never commit to.

        What does “search depth” control?

        Depth bounds how far the conductor expands before it resolves. Depth 1 is a single expansion; higher depth re-expands from the not-taken branches of each level, evaluating a larger, less-redundant region of the option space before a single commitment. A deeper search is a superset of a shallower one, so it never returns a worse result.

        Does it ever decide on its own?

        No. Commitment is always authored — by an automated verification step or by a person. The conductor expands and scores candidates and keeps the field open; it selects one only when an author commits, and only a candidate at or above the threshold.

        How is correctness verified?

        Each module has a deterministic assertion suite and is checked by a mutation-testing gate that alters one operator at a time and requires the suite to detect the change. Both run in continuous integration on every push. Surviving mutants are either killed with a new test or recorded as reviewed equivalents with a written rationale.

        What are the dependencies and runtime requirements?

        None at runtime. The modules are pure ES modules with no build step and no packages. The demo runs entirely in the browser and works offline as a PWA; the tests and CI run on Node.

        Can I extend it?

        Yes. Register a new organ against the core — supply how it expands candidates, how it scores them, and optionally how it commits — and the conductor calls it in the loop. Existing engines are adapted, not rewritten: an adapter routes their generated-and-discarded branches into the shared index. See wire.mjs for three worked examples.

        Lineage

        Origins & acknowledgements

        fall-os is one node in a longer line of work. Its architecture — a single shared engine, an authored control loop, and a content-addressed record of the alternatives — consolidates ideas developed across that lineage rather than inventing them wholesale.

        Design line

        The assos line

        fall-os shares the governing principle of the assos line of sovereign systems: a system owns its own logic, runs self-contained and offline, and carries its own verification — no external service is required to trust it.
